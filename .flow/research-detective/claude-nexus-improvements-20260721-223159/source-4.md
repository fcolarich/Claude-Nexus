## Capture-side patterns (compare against Nexus's `reflector.ts`)

- **Observer-Reflector Memory Extraction** (AnythingLLM pattern) — Nexus's `reflector.ts` already implements this two-phase shape (read transcript window → extract candidates → dedup → insert), so this atom validates the existing architecture rather than exposing a gap. Worth noting explicitly in the synthesis as "already implemented, no action needed."
- **Signal-Based Selective Capture** (ATOM-425, converged across pi-supermemory/pi-muninn-mem/pi-simple-memory) — scores turn content against a signal rubric *before* writing, discarding low-signal turns (acks, filler, repeated context). Nexus's reflector has an "observer gate: skip LLM if no signal" per source-1.md, which is directionally the same idea — but the atom implies a *pre-LLM* heuristic rubric, whereas Nexus's gate (per source-1.md) appears to gate the *entire extraction call*, not filter individual candidates post-extraction. Worth checking whether `refineCandidates` in extract.ts applies signal scoring per-candidate or just drops narration — if it's just narration-dropping, a rubric-based pre-filter could reduce Haiku calls further.
- **Secret-Redaction Memory Guard** (ATOM-429) — screens memory write payloads for secrets/API keys/tokens before persisting. No evidence in source-1.md that Nexus's capture path screens for secrets before writing to the memories table. **Gap**: transcripts frequently contain pasted credentials, tokens, or config — an unscreened capture path can permanently persist a secret into `nexus.db` and its markdown exports (`~/.claude/memories/exports/`), which then gets re-injected into future sessions and the auto-memory MEMORY.md pipeline. This is a real risk given ADR/DDR context confirms exports are file-based and git-adjacent.

## Consolidation patterns (compare against Nexus's decay/ranking)

- **Memory Consolidation Pass** (ATOM-426, 4 independent sources: pi-simple-memory, pi-muninn-mem, pi-supermemory, pi-extension-memory-helper) — a *separate offline step* that reads captured entries, merges duplicates, prunes stale entries, rewrites a compact summary — distinct from the inline capture path, run on schedule or explicit trigger. Nexus has `nexus_consolidate` as an MCP tool (per tool listing) but source-1.md's code review didn't confirm whether it implements merge+prune+rewrite or just a subset. Four independent sources converging on this exact pattern is a strong signal it's a load-bearing feature, not a nice-to-have.
- **Background Memory Consolidation** (ATOM-383) — explicitly frames this as solving *write contention*: a scheduled consolidation agent processes ephemeral outputs after agents are idle, decoupling the critical path from memory writes. Relevant given Claude Nexus's DB is global (single `nexus.db` shared across all projects/sessions per prior session memory) — concurrent sessions across projects could hit SQLite write contention. Worth checking whether Nexus's capture path (reflector.ts) has retry/backoff on `SQLITE_BUSY`, analogous to the atom's `db_utils.retry_sqlite` pattern.
- **MEMORY.md Size-Cap Guard** (ATOM-428) — hard line/byte ceiling (200 lines / 25KB) on exported memory files before injection; over-cap triggers truncation or a consolidation pass rather than injecting an oversized block. Nexus's `exportAll()` (per prior session memory) materializes to `~/.claude/projects/MEMORY.md` for Claude Code's native auto-memory feature — **no evidence of a size cap on this export**. An unbounded MEMORY.md defeats the point of curated recall (this is exactly the class of problem ADR-013's git-root work was solving for project slugs, but for a different axis — content volume rather than identity).

## Recall/injection patterns (compare against Nexus's `recall.ts` + prompt-runner)

- **Pi-Hindsight Recall Budget Pattern** — per-phase `recall_budget` (item count) + `recall_max_tokens` cap, with dual-bank (project vs. `#global`-tagged) architecture. Nexus already has a token budget walk (full→titles-only per source-1.md) and dual-bank query (project + global/shared) — this atom validates the existing design closely; no clear gap, but confirms the "full body until budget, then titles-only" degradation strategy (rather than a hard cutoff) is the better-practiced approach, which Nexus already does.
- **Single-Injection-Per-Session Recall** (ATOM-427, 4 independent sources) — memory context injected exactly once per session, not repeated per turn, to prevent compounding token cost. Nexus's `prompt-runner.ts` does per-session dedup on UserPromptSubmit (per CLAUDE.md's key-files table: "injects relevance-floored recall (top 3-5, per-session dedup)") — this appears aligned already. Confirm dedup is truly once-per-session-per-memory, not just once-per-identical-query, since a user could trigger the same memory twice via differently worded prompts.
- **Scoped Recall Filter** (ATOM-169) — recall triggered only on raw user input messages, excluding tool outputs/hook feedback/meta-prompts, to prevent tool-call noise from poisoning the recall query. Relevant to `prompt-runner.ts`'s UserPromptSubmit hook — if it's only wired to UserPromptSubmit (as CLAUDE.md's key-files table suggests), this is already satisfied structurally, since UserPromptSubmit only fires on actual user messages, not tool output.
- **Memory Scope Parameter** (ATOM-382, converges across LangChain memory/backends/async-subagent docs) — explicit `scope` field (`agent`/`user`/`session`) on read/write calls so one store can route without needing separate clients, preventing memory bleed across agents sharing a store. **Directly actionable gap**: Nexus's memories table has a `scope` column already (per source-1.md's schema summary — "scope, review_status..."), but it's unclear from the code review whether MCP tools (`nexus_remember`, `nexus_search`) expose `scope` as a *caller-settable* parameter or whether it's inferred implicitly from project-slug resolution alone. If it's the latter, subagents sharing a project (e.g. flow phases with different concerns) can't isolate their memories from each other within the same project scope. Worth a direct code check of `mcp/server.ts`'s zod schemas for `nexus_remember`/`nexus_search`.
- **Deferred Recall Injection** (ATOM-476, 5 independent sources) — retrieval fires async at turn start, held until needed, injected without blocking; write-back happens after turn end. Nexus's MCP tools are synchronous request/response (stdio transport) — if `nexus_search`/`nexus_recall` calls block the turn while waiting on embedding generation (Ollama round-trip) + SQLite query, this pattern suggests prefetching recall in parallel with early turn processing rather than serially blocking. Given ADR-006 already fixed a blocking-startup problem (33s event-loop block) by moving indexing off the MCP server's critical path, the same instinct — don't block on synchronous work — could apply to recall on hot paths, though verify whether current latency actually justifies it (premature optimization risk if Ollama embedding calls are already sub-100ms).

## Retrieval/reranking patterns (compare against Nexus's cross-encoder reranker + FTS5)

- **Pi-Session-Search FTS5 Hybrid** — FTS5 exact-phrase index + embedding semantic search, merged via **Reciprocal Rank Fusion (RRF)**, wired so session search (high precision) fires before semantic memory (high recall). Nexus already has FTS5 + sqlite-vec (per CLAUDE.md tech stack) and an 18-tool MCP surface including `nexus_search` described as "hybrid BM25+dense" (per source-1.md) — **but no evidence the fusion method is RRF specifically**, versus a simpler weighted-sum or sequential-fallback merge.
- **Reciprocal Rank Fusion** / **Reciprocal Rank Fusion Retrieval** (ATOM-285 + companion) — `1/(k+rank)` formula, summed across systems, k=60 typical, requires **no threshold tuning** (rank-position-based, not score-based) — contrasted with Nexus's current reranker threshold of 0.2 (per source-1.md's config.ts findings) and min_similarity floor of 0.55 for semantic recall, both of which *are* tuned thresholds. If Nexus's current hybrid merge is threshold-based rather than RRF, this is a concrete, low-effort, well-evidenced improvement: replace tuned-threshold fusion with RRF to remove a class of tuning fragility (thresholds that drift as embedding models change, e.g. if mxbai-embed-large is ever swapped).
- **Two-Stage Retrieval Pipeline** (ATOM-495, Jina) — broad-recall ANN search produces a candidate set, then a cross-encoder reranker precision-sorts it; cites **+8% hit rate, +33.7% MRR over cosine-only retrieval**. Nexus already has this shape (per source-1.md: "reranker cross-encoder fallback" via jina-reranker-v2-base-multilingual, currently **disabled by default**). This is the single most directly actionable finding: the KB independently corroborates (via a different citation than the web source used in the current synthesis draft) that Nexus's own disabled-by-default reranker is worth enabling, with a quantified expected improvement.
- **Listwise Reranking** (ATOM-500) — scores all candidates jointly in one pass (vs. pointwise/pairwise), capturing cross-document relevance signal; jina-reranker-v3 hits BEIR 61.94 at 0.6B params. Nexus's config references jina-reranker-v2 — v3 is a newer, smaller, stronger listwise model. If reranking gets enabled (per above), evaluate v3 over v2 at config time rather than defaulting to the older pinned version.
- **Late Chunking Embeddings** (ATOM-498) / **Matryoshka Embedding Truncation** (ATOM-496) — Jina-specific embedding techniques (context-aware chunk embedding; post-hoc dimension truncation retaining 90%+ quality at 64d). Both are Jina-API-specific and don't directly apply to Nexus's Ollama/mxbai-embed-large stack unless Nexus considers migrating embedding providers — flagged as **lower-priority / not directly actionable** without a provider change, but Matryoshka-style truncation is a generalizable idea (mxbai-embed-large itself supports MRL truncation) worth a footnote rather than a top-line recommendation.
- **Search Fallback Degradation Chain** (ATOM-358) — vector search first, FTS5 on miss, lexical LIKE scan as last resort — fallback triggers only on **empty results**, never on error, so queries never silently return zero. Worth checking whether Nexus's `nexus_search` degrades gracefully when the embedding backend (Ollama) is unreachable, or whether it errors out entirely — this is a resilience gap distinct from ranking quality.

## Design-principle framing

- **Retrieval-over-Storage Framing** (High-signal atom) — "agent intelligence is defined by what it retrieves under token constraints, not what it stores... every memory write decision should be evaluated against the retrieval query it will serve." This atom explicitly names Claude Nexus as an application target ("Apply to Claude Nexus memory writes: each entry must have a declared retrieval query it serves"). This is a good high-level lens for prioritizing the rest of this list: capture-side improvements (signal filtering, secret redaction) matter less than recall-side improvements (RRF, reranking, scope isolation) if the goal is retrieval quality — but both matter, since bad capture pollutes what's available to retrieve.
- **Wikilink Memory Store** (ATOM-141) — contrasting design (memex): flat-file, wikilink-based, **no embeddings**, chosen for auditability/determinism over semantic recall. Relevant as a documented alternative-architecture datapoint, not a recommendation — Nexus's embedding-based approach is a deliberate tradeoff (recall power over pure auditability), and this atom is useful mainly as a citation for *why* Nexus's markdown-mirror export (per CLAUDE.md's `export.ts` description) is valuable: it gives Nexus some of memex's auditability benefit without giving up embeddings, i.e. Nexus's dual-representation (SQLite + markdown mirror) is arguably already a synthesis of both approaches and should be named as a strength, not just infrastructure.

2. **Secret-Redaction Memory Guard (ATOM-429) — CONFIRMED gap.** Grepped `src/capture/extract.ts` and `src/capture/transcript.ts` for secret/token/credential screening logic — no matches beyond the extraction system prompt's general style guidance (line 90-94, which covers tone/format, not content safety). No regex or entropy-based secret scan exists before a memory is written to the `memories` table or exported to markdown. **This is a real, verified, actionable gap** — keep as high-priority.

3. **RRF vs. threshold-based fusion — MIXED, and requires a terminology correction.** Nexus has no "session-start recall path" — ADR-009 explicitly removed the old SessionStart bulk dump (deleted `load-runner.ts` and `recall.ts`'s no-query path) in favor of **per-prompt semantic recall via a `UserPromptSubmit` hook** (`src/capture/prompt-runner.ts`), which fires on every user message, not once at session start. That hook calls `recallByQuery()` in `src/core/recall.ts`. Two distinct recall code paths exist, with two different, verified-by-direct-read merge strategies:
   - `src/core/search.ts`'s `hybridSearchMemories()` (backs the ad-hoc `nexus_search` MCP tool) implements true RRF with `RRF_K = 60` (line 247, matching the atom's convention exactly) — fuses FTS5 rank and vector rank, falls back to FTS5-only if Ollama/vectors are unavailable.
   - `src/core/recall.ts`'s `recallByQuery()` (backs the per-prompt `UserPromptSubmit` recall, i.e. `prompt-runner.ts` — NOT session start) does its own direct `memories_vec` KNN query, floored by cosine similarity or (if the local reranker is enabled) cross-encoder rerank score, and falls back to FTS5 **only when the vector path cannot run at all** (no embedding or no `memories_vec` table — recall.ts:242-243). It does not fuse FTS5 and vector results when both succeed; it does not call `hybridSearchMemories`.
   **Revise the improvement item accordingly**: this is not "add RRF" (it exists, in search.ts) — it's "the per-prompt `UserPromptSubmit` recall path (prompt-runner → recallByQuery) doesn't reuse the RRF fusion logic that the ad-hoc `nexus_search` path already has; consider whether per-prompt recall should call `hybridSearchMemories` instead of maintaining separate vector-KNN-then-FTS-fallback logic, for consistency and to pick up keyword-exact matches that pure cosine/rerank-floored recall can miss even when vectors are available." Do not describe this as a "session-start" path anywhere in the synthesis — that mechanism was removed by ADR-009.
