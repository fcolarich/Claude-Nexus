**Decision:** Add a fifth consolidateMemories() phase, detectContradictions(db, haikuFn), that surfaces candidate-contradictory memory pairs for human review without ever auto-suppressing anything. Pipeline: (1) shortlist via existing memory_links rows with link_type='related' (the 0.70-0.86 cosine band linkMemory() already populates), joined to both endpoint memories, restricted to approved, non-superseded, same scope, same project; (2) a zero-cost divergence pre-filter keeps only pairs where ABS(confidence_a-confidence_b) > 0.3 OR decay_class_a != decay_class_b; (3) a bounded Haiku confirmation call (MAX_PAIRS_PER_RUN=20 per run, oldest-related-link-first) asks a yes/no question -- do these two memories assert genuinely incompatible facts, or are they compatible/just topically related -- returning a structured {conflict: boolean, reason: string}; (4) on confirmed conflict=true, write memory_links rows with link_type='contradicts' BIDIRECTIONALLY -- two directional rows, a->b and b->a, not one -- so nexus_crossref's source-side lookup finds the relationship from either endpoint, plus one diagnostics row (type='stale', atom_id NULL, details JSON {reason:'contradiction', memory_ids:[a,b], haiku_reason}); (5) on conflict=false, a parse failure, or the haikuFn throwing, skip silently with zero writes -- "couldn't check" is never treated as "is a contradiction"; (6) an idempotent self-heal step runs every call: for every durable contradicts memory_links row lacking a matching type='stale' diagnostic, re-insert one. The contradicts link is the durable record; the stale diagnostic is a re-derivable surfacing artifact, because decay.ts:flagStaleMemories periodically runs DELETE FROM diagnostics WHERE type='stale' and re-inserts only its own decayed-memory rows, which would otherwise silently wipe contradiction diagnostics with no path to recreate them (a confirmed pair is excluded from re-shortlisting once it has a contradicts link, so the Haiku loop never revisits it). Nothing is ever deleted, hidden from recall, or auto-superseded by this pass -- a human decides resolution via nexus_health diagnostics or the memory_links graph. This DDR is a hard pre-merge gate (architecture.md KQ4): it must exist before any code touches detectContradictions or its consolidate.ts call site.

**Alternatives:** (a) Write a single memory_links contradicts row per pair (as design.md's Success Criteria literally states) -- rejected in favor of two directional rows because architecture.md's Storage/Data-Flow section (KQ2/Data Flow step 4) explicitly requires both directions for symmetric nexus_crossref lookups from either memory; architecture.md is later and more detailed, so it wins over the design doc's wording, and this DDR records that resolution explicitly per the plan's discrepancy-resolution note. (b) Give contradiction diagnostics a dedicated diagnostics.type value (e.g. 'contradiction') instead of reusing 'stale', so flagStaleMemories' DELETE would never touch them -- rejected because a new CHECK-constraint value requires a table-rebuild migration, violating the feature's no-schema-change constraint. (c) Modify decay.ts:flagStaleMemories to spare contradiction diagnostics from its DELETE -- rejected because the feature explicitly must not touch decay.ts. (d) Abuse the existing related link's confidence field, or add a new link_type/diagnostics.type, as a 'checked, no conflict' sentinel to avoid re-checking cleared pairs on every run -- rejected (schema-changing or corrupts a field other code reads); repeat Haiku cost for still-unflagged pairs is accepted (architecture.md KQ3), bounded by MAX_PAIRS_PER_RUN, with an explicit revisit trigger (add a minimal checked-at column/diagnostics type in a follow-up migration+DDR) if the cap saturates across consecutive runs. (e) Run detection as an LLM-only judgment with no heuristic pre-filter -- rejected as needlessly expensive; the divergence pre-filter and the related-band shortlist are free SQL that shrink the candidate set before any model call. (f) Auto-resolve or auto-suppress confirmed contradictions -- rejected outright per the synthesis's explicit false-positive-risk requirement; both passes in this feature are surfacing-only.

**Reason:** The synthesis document backing this feature (design.md Item 7) treats contradiction detection as carrying real false-positive risk -- a wrongly-flagged pair could lead a human to distrust or discard a valid memory -- and explicitly requires a DDR to exist before the risky code merges (architecture.md KQ4: author after /plan, before /execute touches any contradiction-detection file, so the design is locked before the code exists rather than treated as an afterthought). Recording the bidirectional-write resolution here matters because design.md and architecture.md disagree (one row vs two) and the code (tasks 008-009) needs one unambiguous source of truth to implement and test against; per the plan's resolution, architecture.md -- the later, more detailed document -- wins, and both directional rows are required for symmetric graph lookups. Recording the diagnostics/decay.ts collision resolution here matters because it is a genuine design tension (two features assume ownership of the same CHECK value) resolved by declaring one artifact durable (the link) and the other re-derivable (the diagnostic), which only works if self-heal runs on every detectContradictions call -- a load-bearing behavioral guarantee, not an implementation detail, and thus DDR-worthy rather than left implicit in code comments.
