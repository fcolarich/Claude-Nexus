gemma3:12b (the merge model currently configured as the default in scripts/nightly-distill.ps1, chosen in ADR-20260802190639-f8) was evaluated against the real MERGE_PROMPT via scripts/check-merge-model.mjs on the same six cases used to gate any merge model. Run 1 (GPU saturated, 538 MiB free): 6/6 full identifier retention, avg 83.0s/call. Run 2 (GPU quiet, 7,835 MiB free): 3/6 cases FAILED as 180s timeouts, avg 122.4s/call -- the three that timed out were the hardest and most realistic: 'three-way distinct identifiers', 'identifier-dense (the real failure mode)', and 'shader keywords and paths'. The configured Haiku model (claude-haiku-4-5-20251001 via claude-agent-sdk) on the identical six cases: 5/6 full retention, 1 safe decline, 14.9s/call, zero timeouts. Verdict on measurement, not opinion: gemma3:12b is not viable as the merge model for an unattended sweep -- distill-sweep.mjs aborts a call at 120s, shorter than this gate's own 180s budget, so in production gemma3:12b would time out on its hardest (most identifier-dense) clusters and grind through a multi-thousand-call sweep achieving almost nothing on exactly the clusters that matter most. Two corrections to earlier assumptions, so they are not re-derived: (1) Ollama was already in the pipeline before any of this work -- it serves every embedding (mxbai-embed-large); only the extraction/merge slot is claude-agent-sdk, and the endpoint: line in the extraction: block of extraction_models.yaml is inert unless provider: openai-compatible. (2) VRAM pressure was NOT the cause of gemma's slowness -- freeing 7 GB made it worse (83s to 122s with timeouts), disproving the 'spilling to CPU' hypothesis, since Ollama reported gemma 100% resident (7.49 GB) in both runs; corollary, moving gemma to llama-swap under WSL would make VRAM coordination worse, not better, because embeddings must stay on Ollama so two independent VRAM managers would compete for one 16 GB card with neither aware of the other's allocations. This directly bears on ADR-20260802190639-f8, which configured gemma3:12b as scripts/nightly-distill.ps1's default merge model -- that default has not yet been changed in code as of this note; changing it is a follow-up decision, not made here.
