**Decision:** Corrects and supersedes ADR-20260808214308-a0's root-cause diagnosis. Re-investigation of both flagged residual losses (2/637, 0.3%) traced them to a SINGLE shared cause, not two: any code path that rewrites `memories.body`/`title` in place without recomputing `identifiers` leaves that column stale relative to the new text, and a later merge folding in that stale row inherits the gap. The original ADR's 'backtick-parity regex' hypothesis for the first flagged case (`GetCreatedArea*`) was checked directly against the real production text and found WRONG -- the backtick-span regex correctly enumerates every span including adjacent/close ones (verified directly: 17 backtick-delimited spans in the 'Pooled Buffer Management and Reuse' body, all correctly tokenized, including both `trail.Count < 3` and the later, distinct `trail.Count<3`/`trail.Count<2`). What actually explained both cases: each flagged memory's `updated_at` postdated its `created_at` by minutes, and a fresh extraction on the CURRENT body produced strictly more identifiers than the STORED column -- proof the body was rewritten after the identifiers were captured, by a code path that doesn't touch that column. Two such paths existed: `src/core/distill.ts`'s `sanitize()` step (rewrites title/body for verbose singletons over 800 chars via an LLM 'tighten' call) and `src/mcp/server.ts`'s `nexus_mark_promoted` tool (rewrites body to a thin pointer). Fix: both now compute `unionIdentifiers(existingIdentifiers, extractIdentifiers(newText))` and write that union alongside the rewritten body/title, so a later rewrite can only ADD identifiers to the column, never let it go stale relative to a shrunk body. This mirrors the same set-union principle Phase 1 already uses for distill's merge path -- it turns out sanitize and mark_promoted are two more mechanical mutation sites that needed the identical treatment.

**Alternatives:** Considered leaving the sanitize/promote paths untouched and instead hardening the extractor regex (the original diagnosis's implied fix direction) -- rejected once direct inspection showed the regex was never the problem; a regex change would have fixed nothing and left the real bug in place. Considered re-running a full live-population sweep immediately to confirm literal zero loss end-to-end -- deferred: this session already ran two live sweeps + a rollback against the user's production nexus.db to validate Phase 1 and root-cause this gap; a third unrequested live mutation was judged unnecessary before landing the fix. The fix is instead validated by two new regression tests that reproduce the EXACT real body text from both flagged production cases (Zone Creation Arc Orientation Bug's `GetCreatedArea*`/`ComputeZone*`, and the MERGE_COVERAGE_FLOOR/src/core/distill.ts pointer-rewrite case) and assert the identifiers survive the rewrite. A live re-sweep to confirm literal zero on a fresh window remains a reasonable next step, not performed here.

**Reason:** Recording the corrected root cause matters independently of the fix: an ADR that ships a wrong diagnosis (backtick-parity) alongside a correct fix (union-on-rewrite) would misdirect any future reader trying to understand why the gate failed. The underlying principle generalizes: `identifiers` must be treated as append-only content that every body-mutating code path is responsible for carrying forward, not just the merge path Phase 1 originally targeted. Both fixed call sites are now covered by regression tests using the real failure text, and the full suite (451/452, 1 pre-existing unrelated failure) plus a clean `tsc` build back the change.
