**Decision:** Implemented Phase 1 of the claim-graph redesign (design doc: design/structured-memory branch, C:\Fran\claude-nexus-design\_documents\design-structured-memory.md). Migration v12 adds `memories.identifiers TEXT DEFAULT '[]'`. src/core/identifiers.ts provides a pure, deterministic regex extractor (extractIdentifiers) mirroring the pattern set already validated in scripts/audit-merges.mjs (backtick spans, dotted/pathed/snake identifiers, CamelCase, ALLCAPS/CONST_NAMES, decimals, multi-digit numbers), plus unionIdentifiers() for code-level set-union. src/core/memories.ts's insertMemory auto-extracts identifiers at insert time (or accepts a caller-supplied pre-computed list). src/core/distill.ts's merge path computes mergedIdentifiers = unionIdentifiers(...cluster.map(c => c.identifiers)) from each cluster source's own identifiers column -- never re-extracted from the LLM's merged prose -- and passes it into insertMemory for the new consolidated row. No response_format/constrained decoding is used anywhere in this path (FEAT-20260805151847-eb remains rejected per the design doc's evidence). scripts/backfill-identifiers.mjs deterministically backfills the existing live corpus (additive-only: only touches rows where identifiers IS NULL OR '[]', never overwrites a set-union a merge already wrote). scripts/audit-merges.mjs was extended to recognize retention via the identifiers column, not only via prose text-matching -- this does not loosen the audit for pre-Phase-1 merges (their identifiers column is empty, so they audit exactly as before) and does not change the 16.7% historical baseline.

MEASURED RESULT (validation gate, 2026-08-08): Unit-level, the mechanism is proven -- identifiers.test.ts (18 tests) and new distill.test.ts cases verify 100% identifier retention through the merge path in a controlled fixture where the mock merge prose deliberately drops every identifier the sources carried; the set-union recovers all of them regardless. Full test suite: 449/450 passing (1 pre-existing unrelated failure in reflector.test.ts's vcc_shrunk_at test, confirmed failing identically on the base branch via git stash before any Phase 1 changes). Whole-population live validation: after backfilling 11,950 memories (61,659 identifiers) on the live nexus.db and running a bounded, snapshotted distill sweep (150 candidates, 70 merges created, 179 originals folded), scripts/audit-merges.mjs --all --strict measured 2 of 637 identifiers dropped (0.3%) across 59 merges in the sweep window -- a 98.2% relative reduction from the 16.7% (1,375/8,225) baseline, but NOT the strict zero the Phase 1 gate requires. THE GATE FAILS AS STATED. Root causes were traced to source, not asserted: (1) the backtick-span regex is vulnerable to mis-tokenization when a memory body contains multiple backtick-delimited code spans in close proximity -- confirmed directly: memory 'Pooled Buffer Management and Reuse' contains both a backtick span 'trail.Count < 3' and, later, distinct spans 'trail.Count<3' / 'trail.Count<2'; only the first, spaced variant survived extraction, so the no-space variant was never captured into the identifiers column and the set-union had nothing to recover. (2) distill.ts's pre-existing sanitize() step (~line 527, LLM rewrite of verbose singletons over 800 chars) rewrites title/body in place but never re-extracts or updates the identifiers column afterward -- a confirmed Phase-1 coverage gap independent of the exact run that produced the second flagged loss. Both are extractor/pipeline coverage gaps, exactly the failure class the design doc's own zero-loss gate exists to surface -- not a failure of the set-union mechanism itself, which unit tests prove is airtight once an identifier is captured.

**Alternatives:** (a) Declare Phase 1 passed on the grounds that 0.3% is a 98%+ improvement over baseline -- rejected: the design doc is explicit that 'any loss at all means the mechanism is broken, not underperforming... do not soften the threshold.' (b) Fix the two identified extractor gaps (backtick-parity-aware tokenization; wire sanitize() into the identifiers pipeline) before recording this ADR and re-run the gate -- deferred to a fast-follow rather than blocking this record, so the measured baseline-to-current comparison and the concrete failure examples are preserved for whoever does that follow-up; re-running after a code fix is a NEW measurement, not a revision of this one.

**Reason:** Recording the measured result, root causes, and gate status now (rather than silently iterating until zero is hit) matches the design doc's phase-gating philosophy -- phasing exists to TEST each step empirically, and each phase is gated on the prior phase's measured result -- and the explicit instruction not to soften the threshold. The two root causes are narrow, well-scoped code fixes (backtick-pair-aware regex; sanitize-path identifier re-extraction), not a redesign of the Phase 1 approach, so Phase 2 (claims table, dedupe-and-link) is NOT unblocked by this ADR pending a re-run confirming zero loss -- but the underlying architecture (identifiers column + code-level set-union) is validated by the unit-level proof and should not be revisited.
