**Decision:** Supersedes ADR-20260809012750-1f's still-open status. After landing the sanitize()/nexus_mark_promoted identifier-preservation fix, two further bounded live re-validation sweeps (window `--since 2026-08-08 19:10:27 --until 2026-08-08 23:29:52`: 54 merges; window `--since 2026-08-08 23:29:52`: 4 merges) each still showed small residual losses (2/104 and the earlier 2/637). Direct diagnosis (not assumed) showed these were NOT new bugs: they were leftover staleness from BEFORE the fix landed -- specific source memories had been sanitized during the earlier, pre-fix sweep (`b6ptxnj2j`), so their `identifiers` column was stuck at a smaller set than their current body actually contains, and a later merge (made AFTER the fix, using the correct set-union code) still only unioned from those already-stale sources. The fix prevents NEW staleness; it cannot retroactively repair identifiers that went stale before it existed.

Wrote `scripts/repair-identifiers.mjs`, a two-pass, additive-only (union, never remove) repair: pass 1 recomputes `identifiers = union(stored, extract(current title+body))` for every row, recovering anything the current text names that the stored column missed (fixes leaf-level pre-fix staleness directly: 57 memories, 177 identifiers recovered); pass 2 recomputes every live merge's identifiers as `union(own, union of all its originals' identifiers)`, mirroring distill.ts's own merge-time logic but applied retroactively so an already-made merge inherits what pass 1 just recovered in its sources (612 merges, 2,221 identifiers propagated -- far more than the 57 leaf-stale rows, because this also retroactively applied the Phase 1 guarantee to historical merges made before Phase 1 existed at all, now that their sources carry backfilled identifiers).

After the repair, both previously-flagged re-validation windows audit clean (0/592 and 0/104, 0.0%). Critically, per the design doc's own rule to audit the WHOLE population and never a time window, a full run of `scripts/audit-merges.mjs --all --strict` with no `--since` bound was also run, covering every merge ever made (the original 651-merge baseline corpus plus everything since): **0/12,079 identifiers dropped (0.0%) across 1,518 merges.** The Phase 1 zero-loss gate is MET on the true whole population, not a favorable sample. 47 merges are flagged for the separate, pre-existing coverage-gate signal (semantic cosine similarity, `adr-019`) -- unrelated to identifier loss and outside Phase 1's scope.

**Alternatives:** Considered treating the two small residual losses found in the post-fix re-validation sweeps as an acceptable remainder given they were far smaller than the original 16.7% baseline -- rejected per the design doc's explicit 'any loss at all means the mechanism is broken... do not soften the threshold,' and per the direct instruction not to assume incomplete/partial results are acceptable. Diagnosed both to a specific, distinct root cause (pre-fix staleness propagated through set-union) rather than accepting them as unexplained noise. Considered only re-scanning current live rows (skipping already-superseded originals) for the leaf-repair pass -- rejected: superseded rows remain valid merge sources for any future distill run (they are never deleted, only marked `superseded_by`), so leaving their identifiers stale would let the same propagation bug resurface in a later merge.

**Reason:** The repair script generalizes correctly: it is the same set-union principle already used in distill.ts's merge path and in the sanitize()/mark_promoted fix, applied as a one-time retroactive correction rather than a new mechanism, and it is safe to re-run (additive-only) if any future staleness class is discovered. Auditing the TRUE whole population (no `--since` bound) rather than resting on the favorable sweep-window results is what the design doc's own validation-harness rule requires, and it is the only result that legitimately closes out the Phase 1 gate: 0/12,079 across every merge the corpus has ever produced, including the original 651-merge baseline that measured 16.7% loss under the pre-Phase-1 code. Phase 2 (claims table, dedupe-and-link) is now unblocked on the Phase 1 gate specifically -- it still has its own separate prerequisites (q-006/q-008 DDRs already answered; v13 migration, claim extraction, and Phase 2's own pass bar -- >=1 claim per migrated memory, zero orphaned claims, 15,000-25,000 claim-count band -- not yet built).
