# Claude Nexus — Prioritized Improvement Opportunities (Revised)

*Revision pass. Corrects citation errors, removes unverified placeholder items, adds the previously-missing capture/extraction pipeline coverage, and incorporates direct-source-code corrections from `source-4.md`'s follow-up verification (including a terminology correction: Nexus has no "session-start recall path" — ADR-009 removed the old SessionStart bulk dump; recall is per-prompt via the `UserPromptSubmit` hook).*

## Executive Summary

Claude Nexus's capture and recall pipeline is implemented substantially as documented: semantic dedup at 0.86 cosine, auto-approval at 0.85 confidence, `effectiveConfidence × helpRate` recall ranking, git-root project-slug resolution (ADR-013), and non-blocking MCP startup (ADR-006) are all confirmed directly against source code (`source-1.md`, confidence 0.92). Cross-referencing the project's own ADR/DDR history (`source-2.md`), the LLM Workflow Optimization knowledge-vault atoms (`source-4.md`, confidence 0.90, including a direct-source follow-up verification pass against `mcp/server.ts`, `extract.ts`, `recall.ts`, `search.ts`), and current external practice for agent memory systems (`source-3.md`) surfaces a set of concrete, mostly incremental improvements.

This revision corrects the following from the prior draft (flagged at quality score 0.62): the LLM Workflow Optimization KB is now cited throughout as `source-4.md`; two items that shipped with literal `[TODO: source needed]` placeholders have been removed from the prioritized list and moved to Pending/Follow-up rather than presented as verified findings; the HyMem and MemGuard citations (mismatched to claims those papers don't actually support) have been dropped; the reranker latency figure is now attributed to `source-1.md`/ADR-012 rather than stated as a standalone web fact; the DDR-003/reranking framing has been corrected (reranking reorders post-retrieval candidates — it does not change the `effectiveConfidence × helpRate` selection formula); BECOMER is separated out from the well-documented Zep/Cognee citations and marked unverified; a new top-priority item covers capture/extraction pipeline quality (secret redaction, consolidation, size-capping) — the scope area the prior draft never addressed; and all references to a "session-start recall path" have been replaced with the accurate description — Nexus has no such path (ADR-009 removed it); recall is per-prompt, fired on every `UserPromptSubmit` event via `prompt-runner.ts` calling `recallByQuery()`.

Recommendations are ordered highest-impact/lowest-effort first.

### Terminology: `effectiveConfidence` and the two recall paths

Per `source-1.md` and `source-2.md` (DDR-003), the recall ranking formula is `effectiveConfidence(m) × helpRate`, where `helpRate = help_count / use_count` (defaults to 1.0 when `use_count` is zero) and `load_at_init` memories bypass the min-confidence gate and sort first. **Confirmed by direct read of `src/core/decay.ts`** (resolving the Pending/Follow-up item from the prior draft): `effectiveConfidence(m) = m.confidence * decayFactor(m.decay_class, m.last_verified_at)` — a genuine, already-implemented time-decay mechanism, non-destructive (the stored `confidence` column is untouched; decay is a multiplier recomputed from `last_verified_at`). Decay schedule per `decay_class`: `stable` never decays; `architecture` 30d grace / 60d half-life; `api_contract` 14d/30d; `implementation` 7d/14d. Reconfirming a memory resets `last_verified_at` and instantly restores full effective confidence. This is a well-designed, already-shipped mechanism — no gap here, and Item 6 below (help-rate-trend-based promotion/demotion) is an orthogonal, additional axis, not a duplicate of this time-decay mechanism.

Separately, and confirmed by direct source read in `source-4.md`'s follow-up: Nexus does **not** have a "session-start recall" mechanism — ADR-009 removed the old SessionStart bulk dump (`load-runner.ts` and `recall.ts`'s no-query path were deleted). Recall now happens **per-prompt**: the `UserPromptSubmit` hook (`src/capture/prompt-runner.ts`) fires on every user message and calls `recallByQuery()` in `src/core/recall.ts`. This synthesis uses "per-prompt `UserPromptSubmit` recall (prompt-runner → recallByQuery)" throughout, not "session-start" or "budgeted session-start recall," to match this.

### Confirmed non-gaps (verified against real source — no action needed)

`source-4.md`'s direct-source follow-up (reading `mcp/server.ts`, `extract.ts`, `recall.ts`, `search.ts`) confirmed several candidate gaps identified from KB atoms are already handled, correcting assumptions in the atom-level comparison:

- **Memory Scope Parameter** — `mcp/server.ts` already exposes `scope: z.enum(['global','shared','project'])` as a caller-settable parameter on `nexus_remember`, `nexus_remember_batch`, and as a filter on `nexus_search`. This is not a gap; drop it from any future improvement list.
- **Observer-Reflector two-phase capture shape** — `reflector.ts` already implements read-window → extract → dedup → insert, matching the AnythingLLM pattern the KB atom describes.
- **Recall budget degradation (full-body → titles-only)** and **dual-bank (project/global) querying** — already implemented in `recall.ts`, matching the KB's Pi-Hindsight recall-budget pattern.
- **Scoped recall trigger (`UserPromptSubmit` only)** — `prompt-runner.ts`'s hook wiring structurally satisfies the KB's "exclude tool-output noise from recall queries" pattern, since it only fires on actual user messages.

## Prioritized Recommendations

### 1. Add a secret-redaction guard to the capture path (capture/extraction pipeline quality)

- **Current behavior (verified against real source — `source-4.md` follow-up, grepped `extract.ts`/`transcript.ts`):** No regex or entropy-based secret/credential/token screen exists before a memory is written to the `memories` table or exported to markdown. The only content-shaping logic in `extract.ts` is the durable-knowledge-only system prompt (style/tone guidance), not a content-safety filter.
- **Gap:** Transcripts routinely contain pasted credentials, API keys, or config values. An unscreened capture path can permanently persist a secret into `nexus.db` and its markdown mirror (`~/.claude/memories/exports/`), which then gets re-injected into future sessions and into Claude Code's native `MEMORY.md` auto-memory pipeline — a durable, cross-session leak vector.
- **Recommended change:** Add a secret-redaction check (regex/entropy-based, per the KB's Secret-Redaction Memory Guard pattern) to the capture path before insert/export — either in `extract.ts` post-processing or as a gate in `reflector.ts` before the write.
- **Evidence:** `source-4.md` (ATOM-429, Secret-Redaction Memory Guard; confirmed gap via direct grep of `extract.ts`/`transcript.ts`, not inference).
- **Effort/Risk:** Low-medium effort (one new filter function, no schema change); low risk. This is the highest-confidence, most concretely verified finding in this synthesis and directly closes the scope gap the prior draft omitted entirely.

### 2. Harden the capture/consolidation pipeline beyond secret redaction

- **Current behavior:** `reflector.ts` has an observer gate that skips the entire extraction call when there's no signal (per `source-1.md`), but it's not confirmed whether any per-candidate signal-scoring rubric runs before or after the Haiku extraction call. Nexus exposes an `nexus_consolidate` MCP tool, but `source-1.md`'s code review didn't confirm whether it implements full merge+prune+rewrite or a subset. `exportAll()` materializes memories to `~/.claude/projects/MEMORY.md` for Claude Code's native auto-memory feature with no confirmed size cap.
- **Gap:** Three related KB patterns converge on capture/consolidation quality that Nexus's current design doesn't clearly cover:
  - **Signal-Based Selective Capture** (source-4.md, ATOM-425, converged across 3 independent tools) — a pre-LLM heuristic rubric to filter low-signal turns before the Haiku call, reducing extraction cost; Nexus's observer gate may only gate the whole call rather than filter individual candidates.
  - **Memory Consolidation Pass** (source-4.md, ATOM-426, converged across 4 independent tools) — a scheduled offline merge/prune/rewrite pass distinct from inline capture. Four independent sources converging on this exact pattern is a strong signal it's load-bearing, not optional.
  - **MEMORY.md Size-Cap Guard** (source-4.md, ATOM-428) — a hard line/byte ceiling on the exported memory file before it's consumed by Claude Code's native auto-memory injection, with over-cap triggering truncation or consolidation rather than an unbounded write.
- **Recommended change:** (a) confirm whether `refineCandidates` in `extract.ts` does per-candidate signal scoring or only narration-dropping, and add a pre-LLM rubric filter if it's the latter; (b) confirm `nexus_consolidate`'s current scope against the four-source-converged pattern and extend it to full merge+prune+rewrite if it's a subset; (c) add a line/byte cap to `exportAll()`'s `MEMORY.md` output with truncation-or-consolidate-on-overflow behavior.
- **Evidence:** `source-4.md` (ATOM-425, ATOM-426, ATOM-383, ATOM-428); `source-1.md` for the current observer-gate and `exportAll()` behavior this compares against.
- **Effort/Risk:** Low-medium effort per sub-item; low risk — all three are additive, none require schema changes.

### 3. Reuse the RRF-fused search path in per-prompt `UserPromptSubmit` recall

- **Current behavior (verified against real source — `source-4.md` follow-up, reading `search.ts` and `recall.ts` directly):** `src/core/search.ts`'s `hybridSearchMemories()` (backing the ad-hoc `nexus_search` MCP tool) already implements true Reciprocal Rank Fusion with `RRF_K = 60` (line ~247), fusing FTS5 rank and vector rank, falling back to FTS5-only if vectors are unavailable. But `src/core/recall.ts`'s `recallByQuery()` — which backs the **per-prompt recall path**: the `UserPromptSubmit` hook (`src/capture/prompt-runner.ts`) fires on every user message and calls `recallByQuery()`, not once at session start (ADR-009 removed the old session-start bulk-dump mechanism entirely) — uses a **different, non-RRF strategy**: a direct `memories_vec` KNN query floored by cosine similarity (or cross-encoder rerank score if the local reranker is enabled), falling back to FTS5 only when the vector path cannot run at all (no embedding or no `memories_vec` table — `recall.ts:242-243`). It does not fuse FTS5 and vector results when both succeed, and does not call `hybridSearchMemories`.
- **Gap:** This is not "RRF is missing" — Nexus already built it for the ad-hoc search path. The gap is that the per-prompt `UserPromptSubmit` recall path — the one that fires on every user message and actually injects memories into the conversation — doesn't benefit from the RRF fusion logic the search path already has, and instead uses a strategy where a strong vector match can suppress a keyword-exact FTS5 match even when both signals are available.
- **Recommended change:** Evaluate whether the per-prompt recall path (`prompt-runner.ts` → `recallByQuery()`) should call `hybridSearchMemories` instead of maintaining its own separate vector-KNN-then-FTS-fallback logic, for consistency across the two recall code paths and to avoid missing keyword-exact matches that pure cosine/rerank-floored recall can miss.
- **Evidence:** `source-4.md` (direct read of `search.ts` line ~247 and `recall.ts` lines ~242-243, plus ATOM-285/companion RRF atoms as the general pattern).
- **Effort/Risk:** Medium effort (requires reconciling two recall code paths, possible behavior-change risk for per-prompt injection ordering); low-medium risk since `hybridSearchMemories` is an existing, working implementation being reused rather than new logic.

### 4. Enable cross-encoder reranking for per-prompt recall, correctly scoped against DDR-003

- **Current behavior (verified in code, high confidence — `source-1.md`; ADR-012, `source-2.md`):** `nexus_search` does hybrid BM25+dense retrieval (per item 3). The per-prompt recall path (`recallByQuery()`, via `prompt-runner.ts`) supports optional cross-encoder reranking (jina-reranker-v2-base-multilingual, local HTTP), currently **disabled by default**, with a reranker threshold of 0.2 and a documented one-time latency cost of 50–100ms (`source-1.md` — this figure traces to the source-code review itself, presumptively derived from ADR-012's rationale, not a standalone web claim).
- **Gap:** The reranker exists and is built (ADR-012) but sits disabled by default, so per-prompt recall doesn't benefit from precision-sorted reordering of its candidate set.
- **Corrected framing (nit fix):** Enabling the reranker by default does **not** constitute a change to DDR-003's ranking formula. DDR-003 governs `effectiveConfidence × helpRate` — the mechanism that selects which memories enter the recall window. Cross-encoder reranking is a separate, post-retrieval stage that reorders the already-selected set; it doesn't touch the selection formula. The actual open question is narrower: does reordering the injected context away from confidence-rank order fall within or outside DDR-003's intended scope? That's worth a quick DDR-003 addendum noting the reranker as an explicit post-selection stage, not a revisit of the formula itself.
- **Recommended change:** Enable the existing reranker by default for the per-prompt recall path (one-time cost per prompt, not per background query). `source-4.md`'s KB atoms independently corroborate this via a different citation than the general web claim: the Two-Stage Retrieval Pipeline pattern (ATOM-495, Jina) cites **+8% hit rate, +33.7% MRR over cosine-only retrieval** for exactly this reranking shape. Additionally, `source-4.md` (ATOM-500, Listwise Reranking) notes jina-reranker-v3 is a newer, smaller, stronger listwise model (BEIR 61.94 at 0.6B params) than the currently-pinned v2 — worth evaluating at the same time reranking is enabled, rather than defaulting to the older version.
- **Evidence:** ADR-012 (`source-2.md`) for the existing build; `source-1.md` for the 50-100ms figure and current disabled-by-default state; `source-4.md` (ATOM-495, ATOM-500) for quantified expected improvement and the v2→v3 upgrade option.
- **Effort/Risk:** Low-medium effort (config flag flip + optional model version bump); low risk since the reranker path already exists and is currently opt-in. **Note:** since reranking now runs on every prompt (not once per session), re-verify the 50-100ms figure holds at that call frequency before enabling by default — this is flagged as a re-check, not a new claim.

### 5. Replace the 4-chars/token heuristic with a real tokenizer for recall budgeting

- **Current behavior (verified in code, high confidence — `source-1.md`):** `recall.ts` estimates token cost via a flat 4-characters-per-token heuristic when walking memory bodies to fill the 2000-token recall budget, falling back to titles-only with an elision message once the budget is exhausted.
- **Gap:** A flat character-count heuristic misestimates token cost for code snippets, ADR citations, and non-English text — all common in this system's memory bodies — which can cause premature elision (cutting off high-value context) or budget overrun.
- **Recommended change:** Swap the heuristic for a real tokenizer count (e.g., a lightweight BPE approximation matching the target model's tokenizer) when estimating memory body cost in the recall walk.
- **Evidence:** Direct code finding, `source-1.md` (recall.ts token estimation). No ADR/DDR governs this specific mechanism, so no conflict.
- **Effort/Risk:** Low effort, low risk — localized change to one estimation function, easily tested by comparing estimated vs. actual token counts on real memory samples.

### 6. Adaptive promotion/demotion using help_rate trend, not just static thresholds

- **Current behavior (verified in code + docs, high confidence — `source-1.md`, `source-2.md`):** The schema already tracks `help_count`/`use_count` (feeding `helpRate`) and has 6 promotion targets and a `promotion_target` field. Auto-approval is a static 0.85 confidence gate (DDR-baseline); there is no described mechanism that demotes a memory based on a poor help_rate trend accumulated over time.
- **Gap:** Static thresholds don't account for memories that were initially useful but have since become low-value (low help_rate accumulating over many uses) or vice versa.
- **Recommended change:** Add a periodic (e.g., CLI `prune` or background job) pass that demotes or flags memories whose help_rate has stayed low across a meaningful number of uses, using the existing `promotion_target`/`decay_class` fields rather than introducing new schema.
- **Evidence:** Existing schema fields already support this (`source-1.md`). *Citation correction:* the prior draft attributed this pattern to "HyMem," but HyMem's actual contribution (dynamic retrieval scheduling / dual-granularity storage) doesn't describe help-rate-based promotion/demotion — that citation has been dropped rather than replaced with an unverified substitute, per the anti-fabrication rule. This recommendation now stands on the existing-schema evidence alone (`source-1.md`), not on an external paper citation. `[TODO: verify]` — if external literature support is wanted before implementation, a follow-up read of the actual HyMem/H-MEM papers is needed; none of the four declared sources verify a specific paper for this exact mechanism.
- **Effort/Risk:** Medium effort (new scheduled job + threshold tuning), low-medium risk since it builds on existing fields rather than replacing the auto-approval gate. Does not contradict DDR-baseline — additive.

### 7. Add basic memory conflict/staleness detection (governance gap)

- **Current behavior (verified in code + docs, high confidence — `source-1.md`, `source-2.md`):** Deduplication merges *semantically similar* memories (0.86 cosine) and re-confirms them via `touchMemory`. Extraction normalizes ADR citations to reference pointers specifically to keep canonical documents current. There is no described mechanism for detecting *contradictory* memories (e.g., a superseded decision still present at moderate confidence).
- **Gap:** `source-3.md`'s web research notes a governance gap across most production agent-memory systems: none manage upstream knowledge-base freshness, and stale/contradictory memories can degrade output quality despite perfect episodic recall. Nexus's ADR-pointer normalization solves this for ADR-labeled memories only; general facts/decisions have no equivalent safeguard.
- **Citation correction:** The prior draft attributed this finding to "MemGuard." MemGuard is an adversarial-ML defense system for membership-inference attacks on deep neural networks — unrelated to agent memory governance. That citation has been dropped; the governance-gap finding itself is retained because it's independently present in `source-3.md`'s general summary (not solely attached to the MemGuard mislabel).
- **Recommended change:** At extraction or recall time, add a lightweight contradiction check (e.g., flag memories whose semantic neighbors have significantly different confidence/decay_class, or whose source ADR/DDR has since been superseded) surfaced to the user or auto-demoted.
- **Evidence:** `source-3.md` (governance-gap finding, web-only, moderate confidence); existing ADR-normalization behavior shows the project already recognizes this class of problem for one memory type (`source-1.md`).
- **Effort/Risk:** Medium-high effort (new detection logic, no existing schema support for "supersedes" relationships); medium risk — false positives could suppress valid memories. Should be scoped as its own design decision (new DDR) before implementation.

### 8. Audit the 18-tool MCP surface against grouping best practices

- **Current behavior (verified in code, high confidence — `source-1.md`):** MCP server exposes 18 tools (`nexus_search`, `nexus_recall`, `nexus_context`, `nexus_remember_batch`, and others per `source-1.md`/file-map). ADR-011 already introduced a batch-write tool specifically to reduce 1:1 tool-to-operation calls (`source-2.md`).
- **Gap:** Current web guidance (`source-3.md`) recommends avoiding 1:1 tool-to-endpoint mapping and grouping related operations; 18 tools is a large surface and it's not established whether further consolidation beyond the ADR-011 batch tool is warranted.
- **Recommended change:** A lightweight audit of the 18 tools against actual usage patterns (which tools are called together, which are rarely used) to identify grouping candidates — not a prescriptive redesign, since the project has already made one deliberate consolidation move (ADR-011).
- **Evidence:** ADR-011 batch-write precedent (`source-2.md`); MCP tool-grouping guidance (`source-3.md`, moderate confidence — web-only, general guidance not Nexus-specific).
- **Effort/Risk:** Low effort (audit only, no code change required to start), no risk until a specific consolidation is proposed.

### 9. (Long-term, lower priority) Consider structural/graph memory only if flat-relational limits are actually hit

- **Current behavior (verified in code + docs, high confidence — `source-1.md`):** Memory storage is flat SQLite (WAL + FTS5 + sqlite-vec) with typed fields (`memory_type`, `decay_class`, `scope`, `promotion_target`) — no temporal knowledge graph. `source-4.md`'s Wikilink Memory Store atom (ATOM-141) is a documented alternative-architecture datapoint (flat-file, wikilink-based, no embeddings, chosen for auditability over semantic recall) — relevant context, not a recommendation, and worth naming: Nexus's dual-representation (SQLite + markdown mirror via `export.ts`) arguably already captures some of that auditability benefit without giving up embeddings.
- **Gap:** Competing systems (Zep, Cognee — both well-documented, production systems per `source-3.md`) suggest graph/structural approaches can outperform pure vector storage on some benchmarks. A third citation in the prior draft, "BECOMER" (claimed 94.4% LongMemEval with zero tokens via structural memory), has **not been independently spot-checked** and is not a widely-documented system in the reviewed literature. `[TODO: verify]` — treat the BECOMER benchmark figure as unverified; do not use it to justify a design decision without confirming the paper/system exists and the number is real.
- **Recommended change:** Not recommended as a near-term change. The current flat-relational design aligns with the project's own stated code-style philosophy (minimal abstraction, flat codebase) and the flat schema already supports typed relationships via `promotion_target`/`decay_class` without a graph engine. Revisit only if a concrete retrieval-quality problem is observed that the current schema cannot address.
- **Evidence:** Web findings on graph/structural memory systems (`source-3.md`, moderate confidence for Zep/Cognee; low/unverified confidence for BECOMER specifically — flagged separately per the anti-fabrication rule rather than bundled with the better-documented citations). `source-4.md` (ATOM-141) for the Wikilink alternative-framing context.
- **Effort/Risk:** High effort, high risk — a full architectural rearchitecture. Would require a new ADR and is not justified by current evidence.

### 10. Extend ADR-013's git-root fragmentation fix to the non-git fallback case

- **Current behavior (verified in code, high confidence — direct read of `src/core/project-root.ts`):** `resolveGitProjectRoot()` resolves the canonical project root via `git rev-parse --git-common-dir`, correctly unifying subdirectories and worktrees under one slug (ADR-013's fix). Its own doc comment states this is a "defensive fallback for when git itself isn't available" — when git is unavailable, times out, or the cwd isn't inside a git repository, it falls back to the **raw cwd, unchanged**.
- **Gap:** For any working directory outside a git repository (e.g. a scratch folder, a non-versioned project, or a repo mid-clone before `git init`), the raw-cwd fallback reintroduces exactly the subdirectory-fragmentation problem ADR-013 fixed for the git case: `C:\Fran\project\tools` and `C:\Fran\project` would resolve to two different slugs instead of one canonical slug, since there's no git root to unify them.
- **Recommended change:** Scope is intentionally narrow — this doesn't need ADR-013's git-based solution generalized, just a decision on whether the non-git case matters enough to fix (e.g. via nearest-`package.json`/`.git`-sibling heuristics, or explicitly documenting the fallback as an accepted limitation for non-git projects rather than a silent gap).
- **Evidence:** Direct code + comment read, `src/core/project-root.ts` (this synthesis's own verification, not `source-1.md`/`source-4.md`, since neither source's original review covered this function's fallback branch).
- **Effort/Risk:** Low effort to document as an accepted limitation; medium effort if a non-git resolution heuristic is built. Low risk either way — purely additive or documentation-only.
